# 채팅방 목록의 기존 테스트 확인 기록

- 확인 일자: 2026-10-17
- 대상 API: `GET /subjects/{subject-id}/chats/rooms`
- 확인한 코드: `codex/feature-error-reporting`, 커밋 `9bbbfdb77c9b7675015fd21e6061c704aa9748e2`

## 확인 결과와 범위

이 체크아웃에서 **실제 채팅방 컨트롤러·서비스의 업무 결과를 assertion으로 검증하는 자동 테스트와 기존 BDD 시나리오는 찾지 못했다.** 실제 API를 호출하는 성능 측정 스크립트와 과거 수동 확인 기록은 있다. 이 둘을 자동화된 업무 테스트와 구분한다.

확인 범위는 `src/test`, `load-gen`, `scripts`, `docs`, `.http`, 저장소의 `.feature`, vendor를 제외한 JavaScript 및 테스트 관련 추적 파일이다. 다른 브랜치, 외부 저장소, 별도 QA 시스템은 확인하지 않았다. 따라서 noteu 전체에 테스트가 없다는 결론은 아니다.

이번 작업은 기존 자료의 감사와 문서 연결이다. 아래 테스트를 새로 작성하거나 다시 실행한 결과가 아니다. 코드에서 관찰한 현재 동작, 문서의 설계 목표, 실제 실행 확인 기록을 서로 바꿔 취급하지 않는다.

## 2. 실제 API를 호출하는 측정 스크립트

| 자료 | 실제 수행 내용 | 확인 범위의 한계 |
|---|---|---|
| `load-gen/rooms.mjs:14-35,44-53` | 저장된 세션 쿠키로 채팅방 목록을 반복 호출. 최종 `res.ok` 여부, 네트워크 오류 수, 응답 시간 통계를 기록 | `:30`은 본문을 문자열로 소비할 뿐 JSON을 검사하지 않음. 정확한 상태 코드, 방 내용, 참가자, 정렬을 검증하지 않음 |
| `load-gen/polling.mjs:15-27,35-44` | 여러 세션으로 같은 목록 API를 주기적으로 호출하고 성공/오류 수를 출력 | 응답 본문 검증, 업무 결과 assertion이 없음 |
| `scripts/measure-n1.sh:17-29` | 시드 후 목록 측정을 반복하고 MySQL 카운터 차이로 평균 쿼리 수를 출력 | 기대 쿼리 수 또는 성능 기준을 자동 assertion하지 않음 |
| `load-gen/login.mjs:9-35` | 로그인 리다이렉트 위치와 세션 쿠키 존재를 확인해 측정용 세션을 준비 | 세션 준비 확인이며 목록 API의 비로그인·세션 만료 정책을 검사하는 테스트가 아님 |
| `load-gen/sse.mjs:19-73`, `scripts/measure.sh` | SSE 연결·재연결 및 폴링과의 부하를 측정 | 채팅방 목록의 JSON 업무 결과를 assertion하지 않음 |

목록 측정 스크립트의 `fetch`는 리다이렉트를 기본으로 따라간다. 따라서 최종 응답이 2xx였다는 기록만으로 원래 API가 200 JSON을 반환했다고 확정할 수 없다. `res.ok`는 정확히 200이 아니라 2xx 여부다.

`rooms.mjs`와 `polling.mjs`는 HTTP/네트워크 실패를 오류 수에 집계한다. 오류 수가 있다는 이유만으로 실패 종료 코드를 반환하지 않는다. 통계 출력은 자동 회귀 테스트의 합격 판정과 다르다.

`scripts/seed-chat-data.sh:18-27`은 로그인 회원과 상대 회원이 참여하는 방 및 메시지를 준비하는 코드다. 데이터 준비 자체를 응답 검증으로 계산하지 않는다. 이 감사 과정에서는 시드나 데이터 초기화를 실행하지 않았다.

## 3. 수동 요청과 과거 확인 기록

- `ChatHttpRequest.http:31-33`에는 목록 조회를 위한 수동 HTTP 요청 예시가 있지만 응답 assertion은 없다. 인증 값이 들어 있는 원문은 분석 자료에 복사하지 않는다.
- `docs/N+1_검증_가이드.md:15`에는 당시 `/rooms`와 `/rooms/single`의 200 응답을 확인했다는 기록이 있다. 현재 코드로 재실행한 결과나 지속적으로 실행되는 테스트가 아니다.
- 같은 문서 `:230`에는 방 100개 시드 기준 `/rooms`와 `/rooms/v2`에서 `participants`가 빈 방 0건, 상대방 정보 정상 반환을 확인했다는 기록이 있다. **과거 수동 확인**으로 분류한다.
- 같은 문서 `:201-209`는 쿼리 수, 중복 방, 빈 방, 정렬, 빈 방의 마지막 메시지 값을 확인하는 방법을 나열한 체크리스트다. 이 목록 자체는 모든 항목의 실행 완료를 증명하지 않는다.
- 같은 문서 `:239`에는 참가자 관련 수정이 “미착수”라는 오래된 항목이 남아 있다. `:4`, `:17-18`, `:230`의 해결·확인 기록과 상충하므로 문서만으로 현재 상태를 확정하지 않는다.
- `docs/N+1_개선_설계.md:60-68`의 빈 채팅방 포함 등은 설계 목표·제약의 근거다. 실제 자동 테스트가 검증했다는 근거는 아니다.

## 4. 확인되지 않은 업무 검증과 정책

현재 검색 범위에서 다음 결과를 assertion하는 자동 테스트는 발견하지 못했다.

- 비로그인·세션 만료 요청의 상태 코드, 응답 형식, 로그인 이동 여부
- 존재하지 않는 과목 또는 접근 권한이 없는 사용자의 처리
- DB 장애 시 사용자에게 제공할 응답
- 목록 응답 JSON의 필드와 값
- 로그인 회원이 참여하는 방만 반환하는지 여부
- 중복 방 제거, 메시지 없는 방 표시, 최근 메시지순 정렬
- 상대 참가자 정보와 마지막 메시지 정보의 정확성

테스트가 발견되지 않았다는 사실은 해당 동작이 잘못되었다는 판정도, 특정 동작을 해야 한다는 제품 정책도 아니다. 코드의 현재 동작은 `specification.md`의 관찰 근거로 기록하고, 코드와 자료만으로 확정할 수 없는 기대 동작은 사용자에게 확인한다.

## 5. 분석기에 전달하는 방식

`existing.feature`에는 위 감사의 핵심 출처와 제한을 주석으로 넣었다. 실제 기존 BDD 시나리오를 발견하지 못했으므로 새 시나리오를 만들어 “기존 테스트”로 넣지 않았다. 성능 측정·수동 확인·설계 문구를 실행 가능한 Gherkin 테스트로 변환하지도 않았다.

분석기가 읽는 BDD 입력 자체에 필수 감사 내용이 포함되므로, 이 보조 Markdown 파일을 자동으로 읽는다는 가정에 의존하지 않는다. 향후 실제 업무 테스트나 승인된 BDD가 생기면 출처와 검증 범위를 확인해 연결한다.
